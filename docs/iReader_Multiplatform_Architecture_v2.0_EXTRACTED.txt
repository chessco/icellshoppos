iReader Multiplatform Architecture v1.0
Official Architecture Definition — Apple-first, API-first, Hardware-aware
Product: iReader by Pro Buyer
Ecosystem: iCellShop / Pro Buyer
Target platforms: Windows · macOS · iPhone · iPad
Status: APPROVED ARCHITECTURE BASELINE
Strategic priority: iPad POS first; Windows remains the operational and hardware baseline.
A. Executive Summary
iReader will be evolved as a single product architecture with multiple platform runtimes. The existing Windows Electron application is not replaced; it becomes the first production implementation of the new architecture and is refactored incrementally.
The central architectural correction is to explicitly recognize the existing Pro Buyer API as the shared backend platform already consumed by the Windows application and the web application. iPad must therefore consume the same governed API surface rather than introducing a second backend or a parallel business system.
The approved strategy is: Shared Domain + Shared Application + API Contracts + Shared API Client, with platform-specific Presentation and Platform Adapters. Windows uses Electron/React; macOS initially uses the desktop stack with native helpers where hardware requires them; iPhone/iPad use React Native + Expo Development Builds with native Swift modules where justified.
The iPad POS is the first new experience because the business requirement is to provide sales staff with an Apple-native workflow. The first iPad release should focus on inventory, search, QR/camera intake, product/device detail, cart, checkout and receipt/label workflows rather than attempting to reproduce the dense Windows Add Device screen.
Deep inspection of an arbitrary iPhone/iPad remains a desktop-class capability unless a public Apple-supported mobile mechanism is proven. A Device Bridge is therefore retained as an approved architectural capability for cases where an iPad needs a Windows/macOS host to perform device operations.

C. Architectural Principles
One product architecture; multiple platform experiences.
The Pro Buyer API is the central backend/system of record.
API contracts are explicit and versioned.
Shared domain/application logic must not depend on Electron, React or React Native.
Platform hardware access is isolated behind ports/adapters.
Native-quality Apple UX takes priority over maximum visual/code reuse.
The current Windows product is preserved and migrated incrementally.
iPad POS is the first new product experience.
Deep Apple-device inspection is capability-based, not assumed to be universal.
Security, observability and offline behavior are architectural concerns, not later additions.

J. API Platform Architecture
This section is elevated to a first-class architectural concern because the existing Windows application already consumes the Pro Buyer API.
Target model:
Web Client ───────────────┐iReader Windows ──────────┤iReader macOS ────────────┼──→ Pro Buyer API → DatabaseiReader iPad ─────────────┤iReader iPhone ───────────┘
Inventory, Devices, Intake, Checkout, Sales, Users, Stores and Labels remain backend capabilities.
API contracts must be documented independently from UI implementation.
Introduce explicit API versioning.
Create a typed shared API client for iReader.
Normalize errors into machine-readable codes plus operator-safe messages.
Use idempotency keys for retryable mutations.
Use client operation IDs for offline queues.
Do not duplicate business rules in iPad just because the web currently contains them.
Where current API behavior is weak, evolve it compatibly rather than create an iPad-only endpoint family.
The first backend task is an API audit, not a backend rewrite: inventory existing endpoints, authentication, payloads, error behavior and business rules, then identify what must be formalized for iPad.

L. Apple Device Communication Strategy
Windows remains the reference implementation for deep device operations. The existing AppleUsbAdapter is retained and wrapped behind a stable device contract.
macOS should be evaluated as the preferred Apple desktop/bridge host. Public Apple frameworks such as USBDriverKit are relevant for supported driver/device scenarios, but they do not establish a general public equivalent to the desktop iPhone servicing stack for arbitrary iPhone inspection.
iOS/iPadOS must not be designed around private APIs or assumptions that a USB cable grants unrestricted access to another iPhone. External Accessory is intended for supported accessories, and modern Apple accessory/peer APIs should be evaluated for supported workflows.

N. iOS/iPadOS Constraints
No private Apple APIs.
No assumption of arbitrary USB access to another iPhone.
External Accessory/MFi applies to supported accessory scenarios.
Bluetooth and local-network capabilities require appropriate permissions and privacy declarations.
USBDriverKit on supported iPadOS configurations does not imply access to iPhone internal servicing protocols.
App Store distribution requires public/documented APIs and review compliance.
Any required entitlement must be identified before implementation.

P. iPad POS Strategy
The first iPad product should be designed specifically for sales rather than reproducing the Windows Add Device page.
Recommended first flow:Login → Inventory → Search/Scan → Product/Device Detail → Cart → Checkout → Confirmation → Receipt/Label
Camera and QR scanning are first-class mobile capabilities.
Use large touch targets and clear status.
Use sidebar/multi-column patterns where appropriate on iPad.
Support keyboard and pointer input.
Keep the workflow fast enough for repeated retail transactions.
Move secondary/administrative fields into focused sheets or detail sections.
Deep device diagnostics should appear only where the platform can actually supply them.
Q. Windows Refactoring Strategy
Do not perform a large rewrite. Refactor Windows into the new architecture incrementally.
Audit current API consumption and business rules.
Define canonical domain models.
Define API contracts and shared API client.
Introduce application services around existing workflows.
Wrap AppleUsbAdapter behind Device ports without changing its internals.
Wrap printing behind PrinterService.
Introduce secure storage abstraction.
Move business decisions out of renderer/UI code.
Validate Windows parity.
Only then remove obsolete paths.
Windows becomes the first production consumer of the shared architecture rather than a separate legacy branch.

Decision: Electron for Windows/macOS initially
Why: Preserves proven Windows product and hardware workflow; avoids unnecessary rewrite.
Risk / consequence: Review if security/maintenance economics change.
ADR-002 — Mobile framework
Decision: React Native + Expo Development Builds
Why: Native-quality mobile experience with strong TypeScript/domain reuse.
Risk / consequence: Requires native build pipeline and occasional Swift.
ADR-003 — Shared code
Decision: TypeScript domain/application/contracts/API client
Why: Maximizes meaningful reuse without coupling to UI/runtime.
Risk / consequence: Strict dependency boundaries required.
ADR-004 — Repository
Decision: Monorepo
Why: One product, one API contract surface, multiple clients.
Risk / consequence: Requires package governance.
ADR-005 — API boundary
Decision: Pro Buyer API is system of record
Why: Windows already consumes it; iPad should become another client.
Risk / consequence: API must be formalized/versioned.
ADR-006 — API client

Risk / consequence: Must remain independent from UI.
ADR-007 — Device communication

Risk / consequence: More contracts, but prevents false portability.
ADR-008 — Windows migration

Risk / consequence: Migration takes multiple phases.
ADR-009 — Secure storage

AF. Final Architecture
APPROVED:
Pro Buyer API = central backend/system of record.
Shared iReader contracts + typed API client.
Shared TypeScript domain/application core.
Electron + React desktop for Windows and initially macOS.
React Native + Expo Development Builds for iPad/iPhone.
Swift/native modules only at explicit capability boundaries.
Capability-based device adapters.
Current Windows AppleUsbAdapter preserved and wrapped, then refactored incrementally.
iPad POS is the first new product experience.
Device Bridge is an approved optional architecture for mobile-to-desktop device operations.
Monorepo with strict dependency boundaries.
The architectural goal is not to make Windows, macOS, iPhone and iPad identical. It is to make them coherent clients of the same product platform while allowing each operating system to behave natively.
AG. First 10 Implementation Steps
Audit Pro Buyer API endpoints, authentication, payloads, errors and existing Windows consumers.
Create a capability inventory of the current Windows application.
Define canonical shared domain models for Device, Inventory, Intake, Sale, Checkout and Label.
Define versioned API contracts and the shared iReader API Client.
Create the monorepo package boundaries and dependency rules.
Wrap the existing Windows AppleUsbAdapter behind Device capability contracts without changing its implementation.
Wrap existing Windows printing behind PrinterService.
Build the iPad POS foundation: authentication, navigation, inventory, search and QR/camera flow.
Connect iPad POS to the existing Pro Buyer API through the shared API Client and validate real sales workflows.
After iPad MVP validation, refactor Windows business logic onto the shared domain/application layer while preserving production behavior.
AH. Five-Year Architecture Test
If responsible for iReader for the next five years, this architecture would be approved because it preserves the proven Windows product, elevates the existing Pro Buyer API into an explicit platform boundary, gives iPad a genuinely native path, and isolates the highest-risk hardware dependencies behind adapters and an optional bridge.
The architecture avoids two common failures: rewriting a working Windows application before business value is delivered, and creating a separate iPad system that later becomes expensive to reconcile with Windows and the web.
