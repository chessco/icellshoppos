# PAYMENT-03 — iPAD STRIPE READER + PAYMENT CAPABILITIES
## Pro Buyer / iReader POS
## Technical Architecture & Implementation Report

---

### 1. Executive Summary

Phase **PAYMENT-03** successfully establishes the **Multi-Tenant Optional Payment Capabilities** boundary and delivers the **iPad Physical Stripe Reader Integration** on top of the production-tested PAYMENT-02 Backend Payment Foundation.

#### Key Architectural Accomplishments:
1. **Stripe Terminal is 100% Optional**: Non-Stripe distributors and sites operate normally with `CASH`, `TRANSFER`, `STORE CREDIT`, and `OTHER` payment methods. Zero Stripe SDK initialization, zero Connection Token requests, and zero reader errors occur for distributors without Stripe.
2. **Multi-Tenant Capability Hierarchy**: Configurable capabilities at the `Organization` level with granular overrides at the `Site` / location level.
3. **Stripe Terminal Adapter Boundary**: Clean platform infrastructure abstraction (`StripeTerminalAdapter`) and React Context (`TerminalProvider` / `useTerminal`) decoupling the iPad UI from raw SDK calls.
4. **Authoritative Backend Ledger Verification**: The mobile client cannot self-authorize `SUCCEEDED` status. All card-present transactions are strictly verified by the Pro Buyer API against Stripe's authoritative server state before completing the sale.
5. **Ambiguous / UNKNOWN Payment State Recovery**: Network dropouts or reader disconnects during card processing transition to `UNKNOWN`. Blind retries and duplicate charges are strictly prevented; a specialized reverification flow resolves status with Stripe.

### 4. Stripe Official Research

Official Stripe Terminal documentation and SDK guidelines were analyzed:
- **Supported Readers in Mexico (MXN)**:
  1. **BBPOS WisePad 3**: Bluetooth Low Energy (BLE) connection. Recommended for iPad countertop / mobile POS in Mexico.
  2. **Stripe Reader S700 / S710**: Wi-Fi / Local Network / Internet connection. Smart countertop/handheld reader.
- **PaymentIntent Type**: `card_present` with capture method `automatic`.
- **Location Requirements**: Every physical reader must be registered under a valid Stripe Location (`loc_...`) corresponding to the store/site for fraud prevention and regional tax compliance.
- **Connection Token**: Ephemeral tokens generated by the backend with temporary validity (~10 minutes). Secret keys NEVER leave the server.

### 21. Payment Flow

```
Seller Taps Charge
       │
       ▼
1. Backend creates PaymentIntent & PosPayment (POST /api/payments/stripe/create-intent)
       │
       ▼
2. iPad Terminal SDK invokes collectPaymentMethod()
       │
       ▼
3. Customer Taps / Inserts Card on WisePad 3
       │
       ▼
4. iPad Terminal SDK invokes processPayment()
       │
       ▼
5. Authoritative Verification (POST /api/payments/stripe/verify-status)
       │
       ▼
6. Backend verifies with Stripe Server -> Marks SUCCEEDED
       │
       ▼
7. Sale finalized, inventory deducted, thermal receipt generated!
```

### 22. Backend Verification

- Mobile iPad is strictly an operational client; it **CANNOT self-authorize** `SUCCEEDED`.
- Verification endpoint `POST /api/payments/stripe/verify-status` calls Stripe API server-side, checks payment status, and updates `PaymentAttempt`, `PosPayment`, and `StripePaymentRecord`.

---

### 23. UNKNOWN Recovery

- If network drops or the connection times out while Stripe is processing:
  - Attempt transitions to `UNKNOWN`.
  - UI displays an amber warning banner: **"PAGO EN VERIFICACIÓN (UNKNOWN STATE)"**.
  - A dedicated button `[Re-verificar Estado de Pago con Stripe]` allows the seller to query the server without creating a duplicate charge.

---

### 24. Disconnect Recovery

- If the reader disconnects before card presentation: user can reconnect or switch to Cash/Transfer.
- If the reader disconnects during card processing: treated as `UNKNOWN` and verified via backend before allowing another transaction.
