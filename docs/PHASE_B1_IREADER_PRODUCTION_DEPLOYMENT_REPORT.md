## 1. Objective

Stop depending on a developer's laptop to publish iReader releases. Build a GitHub Actions pipeline that builds the Windows installer, generates `latest.yml`/`.blockmap`, publishes them to the same Hetzner box B.0 already wired the website to, and verifies the result remotely — then prove it with a real 0.2.1 → 0.2.2 update.

---

## 2. Existing Actions

Only one workflow existed: `.github/workflows/deploy-hetzner.yml` — deploys the **web app** (Linux/Docker) via `appleboy/ssh-action@v1.2.0`, triggered on push to `main`, using secrets `HETZNER_HOST`, `HETZNER_USER`, `HETZNER_SSH_KEY`, `HETZNER_PORT` (optional, defaults to 22). It has no Windows build step and nothing to adapt for a Windows/NSIS build — this is why a **new** workflow was created (`ireader-release.yml`) rather than modifying the existing one, per the task's own instruction to not duplicate a workflow that could instead be adapted: there was nothing in the existing one that applied to a Windows build.

No git tag convention existed anywhere in the repository (`git tag -l` → empty) — so `ireader-v{version}` (e.g. `ireader-v0.2.2`) is **proposed and used** as a new convention, prefixed to stay distinct from any future web-app release tags, matching the task's own example format.

---

## 3. Workflow

**`.github/workflows/ireader-release.yml`** (new), three jobs:

1. **`build-windows`** (`windows-latest`): `npm ci` at the workspace root (not inside `desktop/` — required because `electron-updater`/`electron-store`/`bplist-parser` are hoisted to the root `node_modules` in this npm-workspaces monorepo, per A.6 §3.1), `npm run build`, `npm run dist:win`, then validates artifacts exist and that `desktop/package.json`'s version, the generated `latest.yml`'s version, and (when tag-triggered) the git tag itself all agree — failing the whole run otherwise. Uploads the three artifacts as a build artifact.
2. **`publish-hetzner`** (`ubuntu-latest`): downloads those artifacts, pins the real Hetzner host key via `ssh-keyscan` (not `StrictHostKeyChecking=no`), writes the SSH private key from the secret to a temporary file (removed at the end via an `if: always()` step), and runs the existing `desktop/scripts/publish-hetzner.mjs` unchanged in its upload logic.
3. **`verify-remote`**: curls the live `latest.yml`, confirms its version matches what was just built, confirms the installer URL resolves (`200`), and confirms an HTTP Range request against it returns `206`.

Triggers: `push: tags: ["ireader-v*"]` and `workflow_dispatch` (so it can also be run manually from the GitHub UI without needing a tag).

---

## 4. Release Trigger

`ireader-v*` git tags (new convention — none existed to respect, per §2) — e.g. `ireader-v0.2.2`. `workflow_dispatch` is also enabled as a secondary trigger, giving the user a way to re-run the pipeline from the GitHub UI without this session needing to push another tag.

## 5. Version Source

`desktop/package.json`'s `"version"` field remains the single source of truth, unchanged from A.6/B.0. The workflow **enforces** this rather than just assuming it: it fails the build if `latest.yml` (generated by `electron-builder`) disagrees with `package.json`, and fails again if the git tag disagrees with `package.json`, whenever the run was tag-triggered. Nothing hardcodes a version anywhere in the workflow, the publish script, or the website.

## 7. GitHub Secrets

Inspected first (§1 of the task): the existing `deploy-hetzner.yml` already references `HETZNER_HOST`, `HETZNER_USER`, `HETZNER_SSH_KEY`, and optionally `HETZNER_PORT`. **This workflow reuses the exact same secret names** — no new secrets were invented, and `publish-hetzner.mjs` (from B.0) was already designed around reusing them.

**This session cannot see whether these secrets are actually configured in the GitHub repository** (secrets are never exposed to any tooling, by GitHub's own design) — their presence is inferred only from the fact that `deploy-hetzner.yml` presumably already works in production. If they are **not** already configured, here is exactly what's needed:

| SECRET | PROPÓSITO | FORMATO | DÓNDE SE UTILIZA |
|---|---|---|---|
| `HETZNER_HOST` | Hostname/IP of the Hetzner server | Plain string (e.g. `1.2.3.4` or a hostname) | `publish-hetzner` job: SSH host-key pinning + `publish-hetzner.mjs`'s `scp` target |
| `HETZNER_USER` | SSH username on the server | Plain string | Same as above |
| `HETZNER_SSH_KEY` | Private SSH key authorized on the server for that user | Full PEM-format private key contents (e.g. `-----BEGIN OPENSSH PRIVATE KEY-----...`) | Written to a temporary file at runtime, deleted after the publish step; never logged |
| `HETZNER_PORT` *(optional)* | SSH port, if not 22 | Plain string/number | Same as `HETZNER_HOST`'s usage |

No value for any of these was invented, guessed, or hardcoded anywhere in this phase's files.

## 8. SSH Configuration

Per the task's explicit instruction **not** to use `StrictHostKeyChecking=no` as a permanent solution: the `publish-hetzner` job runs `ssh-keyscan -p <port> <host> >> ~/.ssh/known_hosts` at the start of each run, pinning the real host key fresh every time, then uses the default (strict) `scp`/`ssh` host-key verification for the actual file transfer — exactly the approach the task itself suggested as acceptable when no pre-existing `known_hosts` artifact exists to reuse. The private key is written to a runner-local temp file with `chmod 600`, referenced only via `HETZNER_SSH_KEY_PATH` (never the key contents) by `publish-hetzner.mjs`, and explicitly deleted in an `if: always()` cleanup step so it can't linger if a later step fails.

## 9. Hetzner Target

**This required a real correction to B.0's design, not an assumption carried forward blindly (per §9 of the task: "utilizar exactamente el path que B.0 haya implementado... NO asumirlo si el reporte/configuración muestra otro").**

B.0 used a Docker **named volume** (`ireader_releases:/data/ireader-releases`). Named volumes have no predictable host-filesystem path — `scp` (what `publish-hetzner.mjs` uses, and what B.0's own report already committed to) cannot write into one directly without first SSHing in and resolving Docker's internal volume storage path, which is fragile and not "simple, reproducible" as the task requires. This gap was not caught in B.0 because B.0 never got as far as actually publishing a file.

**Fix applied:** `docker-compose.prod.yml` now bind-mounts a real host path instead:
```diff
- - ireader_releases:/data/ireader-releases
+ - /srv/ireader/releases:/data/ireader-releases
```
(and the now-unused named-volume declaration was removed). `/srv/ireader/releases` matches the task's own conceptual suggestion (§9) exactly, and is a sibling to — not inside — the web app's git checkout at `/opt/pitaya/icellshop`, so it's never at risk from `git pull`/`docker compose build` operations there. The **container-internal** path (`/data/ireader-releases`) is unchanged, so none of B.0's web-app code (`src/lib/ireader-releases.ts`, the route handler, the `/ireader` page) needed to change at all. `publish-hetzner.mjs`'s default `IREADER_RELEASES_REMOTE_DIR` was updated to match (`/srv/ireader/releases`).

**This directory does not exist on the real server yet** — it will be created automatically the first time the updated `docker-compose.prod.yml` is deployed and the bind mount is created (Docker creates bind-mount source directories on the host if they don't already exist), or it can be created manually (`mkdir -p /srv/ireader/releases`) ahead of time. Not done in this session — no server access (§19).

## 10. Publish Process

`desktop/scripts/publish-hetzner.mjs` (from B.0) was **not replaced** — only its default remote directory constant was updated to match §9's correction. Its upload behavior is unchanged: installer and `.blockmap` uploaded first, `latest.yml` uploaded **last**, so a client polling mid-publish never sees `latest.yml` reference a file that isn't fully present yet. This already satisfies the task's §10 atomic-release requirement — no additional locking/staging mechanism was layered on top, since the existing ordering already closes the specific race condition described.

## 11. Artifact Validation

Implemented as an explicit, fail-fast workflow step (`build-windows` job, "Validate required artifacts exist" + "Validate version consistency"), **before** the publish job even starts (the `publish-hetzner` job `needs: build-windows`, so it never runs if validation fails). Checks: `latest.yml` exists, at least one `.exe` exists, at least one `.exe.blockmap` exists, `latest.yml`'s version matches `package.json`'s version, and (tag-triggered runs only) the git tag matches `package.json`'s version. **Verified locally against a real build** (§16) — all four checks pass against the actual generated `0.2.2` artifacts.

---

## 12. Remote Validation

The `verify-remote` job (runs only `needs: [build-windows, publish-hetzner]`, i.e. only after a real publish attempt) checks, against the live public URL — **not** trusting `scp`'s exit code alone, per the task's explicit instruction:
1. `GET https://probuyer.pitayacode.io/downloads/latest.yml` → expects `200`, then parses its `version:` field.
2. That remote version matches the version this run just built.
3. `HEAD` on the installer URL (built by reading `latest.yml`'s `path:` field and URL-encoding it, the same way the desktop client and the B.0-validated route handler both do it) → expects `200`.
4. A `Range: bytes=0-99` request against that same URL → expects `206` (§13/Range validation).

**None of this has actually run yet** — it requires the pipeline to execute for real (§19).

## 15. Production E2E — UPDATE: EXECUTED, SUCCEEDED

The user authorized pushing and tagging after reading §19's original blockers. What actually happened, in order:

1. **Push to `main`** triggered the existing `deploy-hetzner.yml` (it runs on every push, unrelated to this phase's new workflow) — it **failed**: `docker exec ... npx prisma@6.4.1 migrate deploy` → `Cannot find module 'prisma/config'`. Root cause: that command's Prisma version was hardcoded and stale; the project actually runs Prisma `^6.16.0` (resolved 6.19.2) with a `prisma.config.ts` the old version doesn't understand. **Not caused by this phase's changes** — confirmed by the git-pull diff in the failed run's own log, which touched none of the Prisma files.
2. Fixed by dropping the hardcoded pin, then — when that alone wasn't enough because the production image doesn't bundle the `prisma` CLI at all, only `@prisma/client` — pinning explicitly to `prisma@6.19.2`. **Separately**, the user ran GitHub Copilot's cloud agent, which found the real underlying issue and fixed it properly: `prisma.config.ts` imported `defineConfig` from `prisma/config`, a module that only exists in the full `prisma` package, not the runtime image. Copilot rewrote it as a plain exported object literal — this is the fix that actually matters; the version-pinning was a superseded band-aid, left in place as a harmless extra safety net.
3. **Tag `ireader-v0.2.2`** pushed, triggering `ireader-release.yml` for the first time for real. It failed in `Package Windows installer (NSIS)`: `ENOENT ... chmod '...\7za'`. The user's Copilot cloud agent diagnosed this as needing `USE_SYSTEM_7ZA=true` and shipped that fix — **this diagnosis was wrong**: that env var makes electron-builder look for a literal `7za` (no extension) inside `desktop/`, which doesn't exist on Windows runners at all, producing a *different* ENOENT.
4. Re-pulled the original failure log (the one from *before* Copilot's fix, which nobody had actually read yet) and found the real error: `ENOENT ... node_modules\7zip-bin\win\x64\7za.exe` — the file was simply missing from the hoisted root `node_modules` at the moment electron-builder needed it. Root cause, confirmed directly from the log: electron-builder's own log shows `installing production dependencies` immediately before packaging — a step that **only runs when publishing** (`artifacts will be published reason=tag is defined`), which local builds (never tag-triggered) never exercised. That step reinstalls/prunes dependencies scoped to `desktop/`, and in this hoisted-monorepo layout it collides with the shared root `node_modules`, removing `7zip-bin`'s binary that electron-builder's own packaging step then also needs.
5. Fixed at the root: `"npmRebuild": false` added to `desktop/package.json`'s `build` config — this is the standard, documented electron-builder option to skip that exact step, which this project doesn't need anyway (the app is fully bundled via electron-vite, not electron-builder's own node_modules handling — see A.6 §3.1). **Verified locally first** (`skipped dependencies rebuild reason=npmRebuild is set to false`, followed by a normal successful build) before re-tagging.
6. Re-tagged `ireader-v0.2.2` a second time (annotated tags were deleted and recreated to point at each successive fix, rather than bumping the version for what were pure CI/build-config issues, not product changes) → **full pipeline succeeded**: Build & Package (Windows) ✅, Publish to Hetzner ✅, Verify Remote Release ✅.
7. **Live verification, from outside the server, against production:**
   - `GET https://probuyer.pitayacode.io/downloads/latest.yml` → `200`, `version: 0.2.2`, correct SHA512/size.
   - `GET https://probuyer.pitayacode.io/ireader` → `200`, page shows `0.2.2` live.
   - `Range: bytes=0-99` against the live installer → `206 Partial Content`.
8. **The actual auto-update E2E, against the real live server, not localhost:** built a `0.2.1` client locally with the *production* `publish.url` embedded (confirmed via its packaged `app-update.yml`: `url: https://probuyer.pitayacode.io/downloads`), installed it for real on this machine, launched it, and observed via Chrome DevTools Protocol against the actual running app:
   - `[AppUpdater] Found version 0.2.2` — detected from the real Hetzner-hosted `latest.yml`.
   - Differential update correctly attempted and gracefully fell back to full download (the `0.2.1` blockmap was never published to production, since only `0.2.2` was ever released there — expected).
   - `getStatus()` → `{"phase":"downloaded","currentVersion":"0.2.1","availableVersion":"0.2.2","downloadProgress":100}` — SHA512 verification passed (electron-updater only reaches `"downloaded"` after it does).
   - `install()` invoked → old process exited → the downloaded `iReader by Pro Buyer Setup 0.2.2.exe` installer spawned and ran to completion automatically → app relaunched.
   - **Confirmed final state**: Windows' own uninstall registry entry reads `iReader by Pro Buyer 0.2.2`; the app was running.
9. Test installation fully uninstalled and the updater cache directory removed afterward — no residue left on this machine.

**This closes the loop the entire A.5→A.6→A.7→B.0→B.1 arc was building toward**: a real, currently-installed iReader client, pointed at nothing but the real production URL, detected, downloaded, verified, and installed a real update published through the real CI pipeline — with no mocks, no localhost, and no simulation anywhere in this final test.

## 17. Security

- No secret value is echoed, printed, or logged anywhere in the new workflow — the SSH key is written directly to a file via `printf` into a redirect, never passed as a CLI argument (which would appear in process listings/logs) and never `echo`'d to stdout.
- Host key verification is real (§8) — no blanket `StrictHostKeyChecking=no`.
- The temporary private key file is cleaned up in an `if: always()` step so a failed run doesn't leave it on a (short-lived, ephemeral) GitHub-hosted runner.
- `permissions: contents: read` is set at the workflow level — this pipeline doesn't need to write to the repository, so it isn't granted that ability.
- Nothing in this phase touches AWS, Nginx Proxy Manager, DNS, or any other project's infrastructure, consistent with every prior phase's restriction.

- **This repo's changes** (the new workflow file, the `docker-compose.prod.yml` volume correction, `publish-hetzner.mjs`'s updated default path): all still uncommitted, local-only — reverting is simply not committing/pushing them, or a plain `git checkout`/`git restore` if already committed locally.

## 20. Final Verdict

**A — PRODUCTION DISTRIBUTION VALIDATED.**

Every criterion the task specified for an A verdict was met, with direct evidence (§15): GitHub Actions build succeeded, the Windows installer/`.blockmap`/`latest.yml` were all generated correctly, publication to Hetzner succeeded, HTTPS works, `latest.yml` and the installer are both live and correct on `https://probuyer.pitayacode.io`, HTTP Range requests work (`206`), the `/ireader` website page shows the new version, a real installed iReader client detected and applied the update entirely through the live Hetzner endpoint (SHA512-verified, `quitAndInstall`, silent NSIS reinstall, auto-relaunch, confirmed final version), no regressions were introduced (Apple USB stack untouched throughout — confirmed again via `git diff --stat` showing zero changes to that code across this entire phase), and AWS was never touched or needed.

**This was not a clean first-try success** — three real, distinct CI/build issues had to be found and fixed along the way (a pre-existing stale Prisma pin unrelated to this phase, an incorrect first fix from GitHub Copilot's cloud agent for the 7za issue, and the actual root cause in electron-builder's `npmRebuild` behavior under npm workspace hoisting). Each is documented in §15 with the real log evidence that led to the diagnosis, not just the final passing state — per the task's own instruction not to declare success "solo porque compile," the evidence trail here is the failed attempts and what proved each one wrong, not just the final green checkmarks.

**No workaround was improvised, no error was hidden, and no architecture was changed to avoid this stopping point** — per the task's own §23 (fail fast) and §27 (no more rounds of design), the correct response to "I can't push to your production repo/server without you saying so" is to say exactly that, clearly, once, and stop.
